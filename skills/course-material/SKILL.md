# 授業教材生成スキル / Course Material Generator

app-dev-course リポジトリ群の週次教材(1回分フルセット)を、パイロット
[app-dev-course-1/week06](https://github.com/ken-ty/app-dev-course-1/tree/main/week06)
で確定した型に従って生成する。**week06 が canonical なお手本。迷ったら week06 に合わせる。**

## コース設計思想(全教材に貫通させる)

1. **成果物駆動** — 知識の網羅より「手が動く・ものが残る」を優先
2. **松竹梅** — 課題は3段階。梅=合格、竹・松=加点。学生のレベル差(バラツキ大)を前提とする
3. **非コード領域も正式コンテンツ** — 環境構築・企画・ドキュメント・デプロイ・エラー対応は「準備」ではなく授業本体
4. **エラーは教材** — わざと壊す実演、エラーメッセージの読み方を毎回どこかに仕込む

## 手順

### Step 1: 対象の確認

ユーザーから以下を確認する(会話から自明なら聞かない):

- コース番号 (1/2/3) と week 番号
- 対象リポジトリのルート README にあるシラバス表の該当行(タイトル・到達目標)を読む
- 前後の回とのつながり(前回までの既習範囲を超える内容を書かない)

### Step 2: 生成前の設計合意

いきなり全ファイルを書かず、まず以下を短く提示して合意を取る:

- その回の演習テーマ案(何を作らせるか)
- ライブコーディングの題材と「わざと壊すポイント」
- 松竹梅の差分の付け方

### Step 3: ファイル生成

`weekNN/` 配下に以下を生成する:

```
weekNN/
├── README.md        # 資料本体(下記の必須セクション)
├── slides/slides.md # Marp スライド
├── assignment.md    # 松竹梅課題
├── answer.md        # 解答例(講師が公開タイミングを制御)
└── code/            # サンプルコード(必要な回のみ)
    ├── exercise1/       # 演習スターター(コメントで要件を書く)
    ├── live_coding_done/ # 講師用カンペ(実演手順をコメントで明記)
    └── <demo_app>/      # 導入で見せる完成形(松の参考実装を兼ねる)
```

## README.md の型(必須セクション順)

1. `# 第N回:タイトル` + 前回までの前提を1行
2. **この回の到達目標**(チェックボックス形式、3〜4個)
3. **タイムテーブル**(90分標準フォーマット、下記)
4. 各セクション本文(導入/講義/演習①/解説/演習②/まとめ)
5. **講師メモ**(巻き/余りの調整方法、机間指導の観点、`{{教室環境メモ}}`)

### 90分標準フォーマット

| 時間 | 内容 |
|---|---|
| 0:00–0:10 | 導入:前回の復習クイズ+今日のゴール(完成形デモを先に見せる) |
| 0:10–0:35 | 講義+ライブコーディング |
| 0:35–0:55 | 演習① |
| 0:55–1:05 | 演習①解説+よくあるエラー |
| 1:05–1:25 | 演習②(松竹梅) |
| 1:25–1:30 | まとめ・課題説明・次回予告 |

講義より演習が長い(25分 vs 40分)ことを崩さない。制作回・発表回など特殊構成の回は
タイムテーブルを組み替えてよいが、「先にゴールを見せる」「まとめで次回予告」は維持する。

## slides/slides.md の型

- Marp形式。frontmatter は week06 のものを流用(theme: default, paginate, header に授業名, footer に `{{学校名}}`)
- 90分あたり **12〜16枚**。1枚1メッセージ。コードは1枚に10行まで
- 必須スライド:復習クイズ / 今日のゴール / 演習指示(①②) / よくあるエラー / まとめ+次回予告
- 概念説明には身近な比喩を1つ入れる(例: 宣言的UI=レストランの注文)

## assignment.md の型

- 冒頭に提出先 `{{提出先}}` / 締切 `{{課題締切}}` / 提出物
- 🌱梅(必達・これで合格) / 🎋竹(標準) / 🌸松(挑戦、「自分で調べる」要素を必ず1つ含める)
- **評価の観点** 表(動くこと / 構造 / 自走)
- **困ったら** セクション(エラーの読み方→検索→質問の仕方、の順)

## answer.md の型

- 梅・竹・松それぞれの解答例コードを載せる(松は「一例」と明記し、別解を歓迎する一文を添える)
- 各解答に「つまずきやすいポイント」を1〜2行で添える
- 冒頭に「まず自分で書いてから見ること」の注意書き
- 公開タイミングは講師が制御する(提出締切後に共有する運用を想定)。学生に常時公開するリポジトリ構成にする場合は answer.md を別リポジトリ/ブランチに分離すること

## code/ の型

- Dart/Flutter は `lib/main.dart` 単体で完結させる(学生が丸ごとコピーして動かせる)
- スターターには要件をコメントで書き、書き換え箇所を `─────` で囲って明示
- 講師カンペには実演手順(Step1..N)を冒頭コメントに書く。「わざと壊す」Stepを必ず含める

## 文体・トーン

- 学生向け本文: です・ます調、絵文字は見出し・演習指示に少量(✍️ 🙋 程度)
- 講師メモ: 常体で簡潔に
- エラーを否定的に書かない。「エラーは失敗ではなく情報」のスタンスで統一

## プレースホルダ規約(横展開のため厳守)

- 学校固有値は直接書かない: `{{学校名}}` `{{提出先}}` `{{課題締切}}` `{{教室環境メモ}}` を使う。実値は `config/<school>.md` が持つ
- 学生の実名・学内スクリーンショット・学校の内部事情を教材に書かない

## 生成後セルフチェック

- [ ] 到達目標とタイムテーブルと課題が一貫しているか(目標にない内容を課題に出していないか)
- [ ] 既習範囲を超えた API/概念を無断で使っていないか(使うなら「次回扱う」と明記)
- [ ] 梅が本当に「その回の内容だけ」で完成できるか
- [ ] プレースホルダ規約違反がないか
- [ ] スライド枚数が12〜16枚か
- [ ] answer.md が assignment.md の松竹梅すべてに対応しているか
